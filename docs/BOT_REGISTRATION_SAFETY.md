# Bot registration safety and troubleshooting

A workspace registration previously checked whether a Telegram bot was already present, then used an upsert keyed by the bot ID. Concurrent requests could both pass the check and the later upsert could overwrite the earlier workspace's record. The registration path now checks the full unique `bot_id` index before attempting an insert-only write. Telegram-backed records normally use the deterministic `bot_<Telegram ID>` key; collision returns a validation error and does not overwrite the existing document. Token-free drafts also use insert-only creation. The Next Studio preserves the draft and explains the duplicate or the safe-index failure; the existing Studio receives the safe server message.

If the backend returns **cannot verify safe bot registration**, an operator should inspect database connectivity, index permissions and existing duplicate or malformed `bot_id` values. Do not delete records or drop indexes without a reviewed backup and repair plan. The index verification fails closed; no registration document is inserted by that request. If insertion succeeds but a subsequent defaults, audit or notification write fails, the response is uncertain: refresh the workspace before retrying. These writes are not a transaction, and a partially initialized record may need an operator's review.

This change is not a global Telegram-ID uniqueness guarantee: historical records with nonstandard `bot_id` values, concurrent legacy writers and other update paths require further review. Old or mixed-version backend workers can still execute the former upsert; coordinated deployment and real Mongo/multi-worker tests are necessary. The protection also assumes the verified index is not dropped out of band between checking and insertion. It does not import `/clone` registrations or start a worker.

Token verification still calls Telegram's Bot API, which requires a token in the request path; HTTP exception strings may include that URL. The token-validation helper now logs only a generic failure, never the exception text. This does not audit every other HTTP client, logger, proxy or dependency. Do not share raw logs without redaction.

Synthetic checks: from `VidelBot/`, run `python -m pytest tests/test_bot_registration_contract.py tests/test_bot_token_validation_redaction.py`; the mock-Mongo tests are not proof of real database concurrency. The `next-bot-registration.test.cjs` browser check uses the isolated Next preview fixture and intercepted responses; it does not contact Telegram or production.
